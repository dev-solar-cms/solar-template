Checkout

The checkout flow (cart, login, shipping, payment, confirmation) stays built on real WordPress/WooCommerce pages (/cart/, /checkout/, /checkout/order-received/..., depending on the store's permalink settings), dressed up by the theme's own templates rather than replaced by dedicated views.

Routing and step indicator

Solar_Template\Checkout\CheckoutController::template_include() (hooked on WordPress' template_include filter) serves the theme's own template, checkout.php, as soon as is_cart() or is_checkout() is true — the same controller mechanism already used for the product catalog. This avoids depending on these pages' slug (configurable in the WooCommerce settings), unlike a classic page-{slug}.php template.

checkout.php opens the document with get_header('checkout') / get_footer('checkout'), loading header-checkout.php / footer-checkout.php instead of the site's global templates: the flow deliberately has no primary navigation, mega menu or search, so as not to distract the customer mid-purchase. The minimal header only shows the brand (linking home) and a "100% secure payment" note; the minimal footer only shows legal links, contact, copyright and a secure SSL payment note.

Solar_Template\Checkout\StepIndicator::steps() computes, for each of the 5 steps (Cart, Login, Shipping, Payment, Confirmation), its state — done, active or future — relative to the current step, and template-parts/checkout/step-indicator.php renders it (numbered circles, a progress line, labels), shared by every page of the flow.

Technical decision: the Login, Shipping and Payment steps actually live on a single WooCommerce page (/checkout/, one native form) rather than three separate pages. Checkout\CheckoutController::current_step() therefore only resolves which sub-step is visible on that page's very first load (Login for a guest visitor, Shipping directly for an already logged-in customer) — moving between those three sub-steps afterward happens client-side (assets/js/checkout.js, initCheckoutSteps()), never submitting the form before the final click on the payment button.

Verified end to end in the real Docker environment with WooCommerce active: the cart page shows the indicator with the "Cart" step active and the next four pending; after adding a product to the cart, the checkout page shows "Cart" done and "Login" active for a not-logged-in visitor. No PHP warning or error raised.

Cart

woocommerce/cart/cart.php renders the cart's real line items — Solar_Template\Checkout\CartView::items() computes each one's image, name, variation/engraving metadata, quantity field and price — a coupon code form, and a sticky order summary (woocommerce/cart/cart-totals.php: subtotal, discounts, shipping, total, a button toward the next step).

woocommerce/cart/cart-item-data.php renders an item's metadata (color/size, engraving) as a single inline line ("Color: Black · Size: M") instead of WooCommerce's default definition list, reusing the exact same data (wc_get_formatted_cart_item_data()) — the content stays real, only the presentation changes.

Every cart field and action keeps WooCommerce's own native name, action and nonce (cart[{key}][qty], wc_get_cart_remove_url(), coupon_code/apply_coupon, woocommerce-cart-nonce): changing a quantity, removing an item and applying a coupon all work through a plain form submission, no JavaScript required. The "−"/"+" quantity stepper (assets/js/checkout.js, initCartQuantitySteppers()) only adjusts that same native field's value before submission — same convention as the quantity stepper already in place on the product page.

Technical decision: the "Proceed to..." button explicitly names the next step the customer will actually see ("Proceed to login" for a guest, "Proceed to shipping" for an already logged-in customer) rather than WooCommerce's generic wording, consistent with the step indicator.

Bug found and fixed during real Docker verification: this WooCommerce installation's cart and checkout pages defaulted to the native Gutenberg blocks rather than the classic shortcodes — a classic/non-FSE theme like this one cannot override the PHP templates those blocks bypass entirely (their real content is only hydrated client-side, invisible to any server-side check). Fixed by reassigning both pages' content to the classic shortcodes ([woocommerce_cart]/[woocommerce_checkout]).

Verified end to end in the real Docker environment with WooCommerce active: adding several products to the cart, changing a quantity, removing an item and applying a test coupon (created then deleted after verification) all confirmed working. No PHP warning or error raised.

Login

The checkout page is now organized into panels toggled client-side by assets/js/checkout.js (initCheckoutSteps()): a not-logged-in visitor first sees a "Login" panel (woocommerce/checkout/form-checkout.php), an already logged-in customer goes straight to the "Shipping" panel. No panel is ever submitted before the final click on the payment button — these are just sections of one single native form, shown or hidden.

The login form itself (woocommerce/global/form-login.php) stays real WordPress authentication (wp_signon(), unchanged) — only its presentation is restyled, the native field names, nonce and redirect field stay identical. "Continue as guest" (offered unless an account is required to order) simply switches to the "Shipping" panel — guest checkout is already WooCommerce's native behavior, nothing to enable server-side. "Create an account" (offered when registration is allowed at checkout) also switches to that panel and checks the native #createaccount checkbox that reveals the account-creation fields there.

The Google/Facebook social login buttons are deliberately disabled (disabled, "Not available yet" tooltip) and documented as not implemented — a real OAuth integration would require a third-party service, out of scope for this step.

Technical decision: Checkout\CheckoutController::detach_default_checkout_hooks() detaches the login form and coupon box WooCommerce adds to the top of the checkout page by default, since the former now lives in its own styled panel and the latter is already offered on the cart step.

The step indicator stays in sync across these panel changes: the "Login" step turns done (checkmark), the "Shipping" step turns active and its circle becomes clickable again to go back; a future step's circle stays disabled until it's actually reached.

Verified end to end in the real Docker environment with WooCommerce active: a real login with a test user (created then deleted after verification) correctly redirects to the checkout page and makes the login panel disappear entirely, the customer going straight to the "Shipping" panel with the "Login" step marked done. No PHP warning or error raised.

Shipping

The "Shipping" panel now shows a real two-column layout: real WooCommerce address fields on the left (woocommerce/checkout/form-billing.php/form-shipping.php) in the design handoff's 2-column grid (first/last name, address, address line 2, postcode/ city, country/phone), a sticky order summary on the right reusing the exact same component as the cart page's own sidebar.

Solar_Template\Checkout\CheckoutFieldsLayout::rows() groups known field pairs (first/last name, postcode/city, country/phone) by their bare name — independent of the billing_/shipping_ prefix each field set carries, since both share this same layout logic. A field whose usual partner is missing (a store with no phone field, say) or an unrecognized field added by a third-party plugin still renders alone, full width, rather than being hidden or breaking the layout.

Technical decision: WooCommerce's own default field order puts the country selector right after the name (needed early for tax/shipping calculation), which would pair it with phone ahead of the address fields entirely. CheckoutFieldsLayout::reorder_address_fields() (hooked on the woocommerce_checkout_fields filter) fixes this by only reassigning the display priority of fields it already knows about, leaving any other field a third-party plugin adds untouched.

A store's actually configured shipping methods (Standard/Express, say) render as radio cards (woocommerce/cart/cart-shipping.php, shared with the cart page's own sidebar). This file had stayed WooCommerce's default <tr> markup since the cart step — invalid once nested inside its own summary's <div> — fixed into a proper <div> along the way.

Bug found and fixed during real Docker verification: the order summary (woocommerce/checkout/review-order.php) had lost its woocommerce-checkout-review-order-table CSS class along with its table structure — but that exact class is what WooCommerce's own checkout.js targets to replace this block on every AJAX totals refresh (a shipping method change, an address field change...). Without it, the replacement found no matching element and silently failed: the displayed total never updated. Fixed by keeping that class on the new summary's root element.

Verified end to end in the real Docker environment with WooCommerce active: two test shipping methods (free and €5.99, deleted after verification), simulating WooCommerce's own update_order_review AJAX request directly — the total, the radio cards' selected state and the returned fragment all correctly reflect the method change. No PHP warning or error raised.

Payment

Payment now has its own panel (woocommerce/checkout/payment.php), separate from the "Shipping" panel rather than combined with it as before: the "Shipping" panel now ends with a "Proceed to payment" button that switches to the "Payment" panel without ever submitting the form, and that panel offers a matching "← Back" button. The order summary (#order_review) stays a single, shared DOM element across both panels (hidden only during the Login step) rather than duplicated, so as to never duplicate the id/CSS class WooCommerce's own checkout.js targets for its AJAX refreshes.

Solar_Template\Checkout\CheckoutController::detach_default_checkout_hooks() now also detaches the native hook (woocommerce_checkout_payment, hooked onto woocommerce_checkout_order_review) that would otherwise render the payment method list a second time right after the order summary — the "Payment" panel calls it itself (woocommerce_checkout_payment()), exactly where it belongs.

A store's actually configured payment gateways render as radio cards (woocommerce/checkout/payment-method.php, the same visual convention as the previous step's shipping method cards) with a relevant icon (Solar_Template\Checkout\PaymentGatewayIcons): WooCommerce's own native gateways (direct bank transfer, cheque payment, cash on delivery — no dependency on any third-party payment plugin, this theme installs and assumes none) each get a dedicated icon; any other gateway a store activates later (a real payment extension, say) gets a generic card icon rather than nothing at all.

The submit button reuses the design handoff's own "🔒 Pay [amount]" copy (Solar_Template\Checkout\CheckoutPayment, the native woocommerce_order_button_text filter), computed from the cart's real, current total rather than a fixed string — so it always stays accurate, including after a shipping method change or a coupon being applied.

Verified end to end in the real Docker environment with WooCommerce active: the three native gateways (direct bank transfer, cheque payment, cash on delivery) enabled and correctly rendered with their respective icon, and a full order simulated with the exact request the payment form would submit (?wc-ajax=checkout) — confirmed created with the right payment method and total (test order deleted after verification). No PHP warning or error raised.

Confirmation

The confirmation page (woocommerce/checkout/thankyou.php) now shows a centered recap (gold checkmark, order number, estimated delivery, total paid, shipping address, items ordered, "Track my order"/"Continue shopping" buttons) built from the real, just-placed order's own data (Solar_Template\Checkout\OrderConfirmation::view_model(), the same convention as CartView for the cart page) rather than WooCommerce's default recap.

The estimated delivery is a date range computed from the order's real creation date, with a filterable lead time (solar_template_order_confirmation_delivery_lead_days), ahead of a future admin screen.

Technical decision: Checkout\CheckoutController::detach_default_checkout_hooks() now also detaches the order details table WooCommerce adds by default at the bottom of the confirmation page, redundant with the theme's own recap already showing the same real data in its own style. Each payment gateway's own hook stays in place (e.g. a bank-transfer order's account details), since that is real content the customer actually needs, not a redundancy.

A failed order shows WooCommerce's own restyled error message instead of the success recap, with a button back to that order's payment page.

Verified end to end in the real Docker environment with WooCommerce active: a real order placed through the payment form shows the confirmation with the right data (number, estimated delivery, total, address, items, email) and the right step indicator state; a test order set to the failed status correctly shows the matching restyled branch (test orders deleted after verification). No PHP warning or error raised.
