Product page

single-product.php renders a WooCommerce product's own page. This template is built section by section, same convention as front-page.php for the home page.

Gallery

Solar_Template\Product\ProductGallery::images() reads the product's featured image, then its WooCommerce gallery (WC_Product::get_image_id()/ get_gallery_image_ids()), deduplicated, and returns a flat list (id, URL, alt text). single-product.php computes this list (falling back to WooCommerce's own placeholder image when the product has no image at all) and passes it to template-parts/single-product/gallery.php, which only renders it — same convention as Catalog\ProductCardMapper/template-parts/product-card.php for the product card.

The main image (4:5 ratio) is followed by a strip of thumbnails, one per image — the strip does not render at all as long as the product has a single image. Clicking a thumbnail swaps the main image with no page reload (assets/js/product.js, initProductGallery()), and marks that thumbnail active.

Technical decision: the mockup's "Enlarge" (zoom/lightbox) button is deliberately not built at this stage — its behaviour is not specified beyond the mockup itself, same reasoning as archive-product.php's grid/list view toggle.

Verified end to end in the real Docker environment with WooCommerce active: a product with no image at all confirms the fallback to WooCommerce's own placeholder image (no thumbnail strip); a test product with a featured image and a gallery image confirms the thumbnail strip renders, the first one marked active — test product and images deleted after verification. No PHP warning or error found.

Product panel

template-parts/single-product/panel.php renders the sticky right-hand column (top:120px): badges, title, rating, stock status, short description, a trust badges block and an accordion. Same as the gallery, this fragment only renders already- computed data — single-product.php calls Solar_Template\Product\ProductBadges/ProductPanel/ProductStock and passes the result to it.

Unlike the mockup, whose "NEW"/"SOLAR PREMIUM" badges are always shown, these are computed from real WooCommerce data and may not render at all: "New" as long as the product was published less than solar_template_product_new_badge_days days ago (14 by default, filterable), "Solar Premium" only when the product is marked "Featured" from the edit screen (WC_Product::is_featured()).

The stock status ("In stock"/"Out of stock"/"Available on backorder") is translated through the theme's own catalog rather than reusing WooCommerce's core strings (which use their own text domain, distinct from the theme's) — consistent with the i18n foundation laid at the very start of the project.

Technical decision: the trust badges block and the accordion stay editorial content, exposed through dedicated WordPress filters (solar_template_product_trust_badges/ solar_template_product_accordion_sections) — same convention as the home page's hero/"our story" helpers, ready for the future "Products" administration tab without building that tab now.

Verified end to end in the real Docker environment with WooCommerce active, in both installed languages: a freshly created test product marked "Featured" confirms both badges render, its short description, its (out of) stock status, and the panel's full translation — test product deleted after verification. No PHP warning or error found.

Variations and dynamic price

For a WooCommerce variable product, the panel renders Color and Size selectors — color circles and size buttons — wired to the product's real variations, rather than WooCommerce's native dropdown selects. Each greyed-out, disabled option means no in-stock variation exists for that value, regardless of any other dimension (same static treatment as the mockup's own XXL size, independent of the chosen color).

Solar_Template\Product\ProductVariations builds these selector groups and the variation list passed to JavaScript, reusing the same filterable Color/Size attribute slugs as the catalog filter bar (Catalog\CatalogOptions::color_attribute_slug()/ size_attribute_slug()) — a store only configures this attribute name once for the whole theme. The swatch color comes from Product\ColorSwatch::hex_for_term(): an optional per-term meta value first, then a filterable name/slug → hex map, then a neutral gray — pending a future administration screen to configure it per term.

assets/js/product.js (initProductVariations()) resolves the current selection against the real variation list localized by Product\ProductController::enqueue_script() (window.solarTemplateProduct), updating accordingly: the displayed price (reformatted using the store's real price display settings — decimals, separators, symbol position — never a hardcoded value), the "Add to cart" form's hidden variation_id, and that button's disabled state.

Technical decision: unlike the mockup, whose "Add to cart" button itself displays the price ("Add · {price}"), the price and the button stay two separate elements — a single price location to recompute rather than two to keep in sync. The "Add to cart" form itself stays a standard native WooCommerce form (a plain submission, no AJAX): the attribute_* fields usually real dropdown selects are hidden inputs here, synced by this script on every color circle/size button click — WooCommerce receives exactly the same request it would from native dropdowns.

Verified end to end in the real Docker environment with WooCommerce active, in both installed languages: a test variable product (two colors, two sizes, one combination deliberately out of stock) confirms the selectors render correctly and the initial price range, then an add-to-cart request identical to the one the form would submit once a valid combination is resolved confirms WooCommerce's real cart receives the exact variation and quantity (cart total verified) — test product and variations deleted after verification. No PHP warning or error found.

Custom engraving option

A "Custom engraving" section can be enabled per product — natively, with no dependency on ACF or WooCommerce Product Add-ons (a structuring decision of this project). Solar_Template\Product\ProductEngraving reads three native WooCommerce product meta values: enabled or not, price surcharge (€25 by default) and maximum text length (20 characters by default).

Solar_Template\Product\EngravingAdminFields adds a toggle and two fields to the "General" tab of the WooCommerce product edit screen, using WooCommerce's own native admin field helpers (woocommerce_wp_checkbox()/woocommerce_wp_text_input()) — no third-party meta box framework — and persists them on the woocommerce_process_product_meta hook.

When engraving is enabled for a product, the panel renders a toggle and a text field, inside the "Add to cart" form itself (so their value submits along with it). Turning the toggle on adds the surcharge to the displayed price — the same recalculation mechanism as the Color/ Size variations — and makes the text field required.

Solar_Template\Product\EngravingCart captures the submitted selection into the cart item's own data (truncated to the configured maximum length), adds the surcharge to that item's price on every totals recalculation — recomputed from the product/variation's real price every time, never compounded on top of the already-adjusted price, so the surcharge is never applied on top of itself — shows it as an extra line on the cart/ checkout, and persists it as the resulting order line item's meta: the submitted value ends up in the order, not just the cart.

Verified end to end in the real Docker environment with WooCommerce active, in both installed languages: the admin fields display and save the configured values correctly; an add-to-cart request identical to the one the form would submit once engraving is enabled confirms WooCommerce's real cart receives the price surcharge (cart total verified) and the engraving text truncated to the configured maximum length; a direct simulation of the order line item's creation confirms that text is persisted as its meta — test product deleted after verification. No PHP warning or error found.
