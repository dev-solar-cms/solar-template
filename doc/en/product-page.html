Product page

single-product.php renders a WooCommerce product's own page. This template is built section by section, same convention as front-page.php for the home page.

Gallery

Solar_Template\Product\ProductGallery::images() reads the product's featured image, then its WooCommerce gallery (WC_Product::get_image_id()/ get_gallery_image_ids()), deduplicated, and returns a flat list (id, URL, alt text). single-product.php computes this list (falling back to WooCommerce's own placeholder image when the product has no image at all) and passes it to template-parts/single-product/gallery.php, which only renders it — same convention as Catalog\ProductCardMapper/template-parts/product-card.php for the product card.

The main image (4:5 ratio) is followed by a strip of thumbnails, one per image — the strip does not render at all as long as the product has a single image. Clicking a thumbnail swaps the main image with no page reload (assets/js/product.js, initProductGallery()), and marks that thumbnail active.

Technical decision: the mockup's "Enlarge" (zoom/lightbox) button is deliberately not built at this stage — its behaviour is not specified beyond the mockup itself, same reasoning as archive-product.php's grid/list view toggle.

Verified end to end in the real Docker environment with WooCommerce active: a product with no image at all confirms the fallback to WooCommerce's own placeholder image (no thumbnail strip); a test product with a featured image and a gallery image confirms the thumbnail strip renders, the first one marked active — test product and images deleted after verification. No PHP warning or error found.

Product panel

template-parts/single-product/panel.php renders the sticky right-hand column (top:120px): badges, title, rating, stock status, short description, a trust badges block and an accordion. Same as the gallery, this fragment only renders already- computed data — single-product.php calls Solar_Template\Product\ProductBadges/ProductPanel/ProductStock and passes the result to it.

Unlike the mockup, whose "NEW"/"SOLAR PREMIUM" badges are always shown, these are computed from real WooCommerce data and may not render at all: "New" as long as the product was published less than solar_template_product_new_badge_days days ago (14 by default, filterable), "Solar Premium" only when the product is marked "Featured" from the edit screen (WC_Product::is_featured()).

The stock status ("In stock"/"Out of stock"/"Available on backorder") is translated through the theme's own catalog rather than reusing WooCommerce's core strings (which use their own text domain, distinct from the theme's) — consistent with the i18n foundation laid at the very start of the project.

Technical decision: the trust badges block and the accordion stay editorial content, exposed through dedicated WordPress filters (solar_template_product_trust_badges/ solar_template_product_accordion_sections) — same convention as the home page's hero/"our story" helpers, ready for the future "Products" administration tab without building that tab now.

Verified end to end in the real Docker environment with WooCommerce active, in both installed languages: a freshly created test product marked "Featured" confirms both badges render, its short description, its (out of) stock status, and the panel's full translation — test product deleted after verification. No PHP warning or error found.
