My account

The My Account area stays built on the real WordPress/WooCommerce /my-account/ page (the [woocommerce_my_account] shortcode), dressed by the theme's own templates — woocommerce/myaccount/*.php — rather than replaced by dedicated views. Two endpoints of the theme's own (wishlist, support request) are added on top of WooCommerce's native ones.

Sidebar and dashboard

woocommerce/myaccount/my-account.php now places the navigation and content in a 260px 1fr grid (.account-layout) instead of WooCommerce's default stacked layout. woocommerce/myaccount/navigation.php delegates rendering to template-parts/account/sidebar.php: a user info block (avatar/name/email, Solar_Template\Account\AccountProfile) followed by an icon-based navigation (Solar_Template\Account\AccountNav).

Solar_Template\Account\AccountEndpoints fully rebuilds the account menu in the design handoff's own order and wording (Dashboard, Orders, Wishlist, Addresses, Downloads, Support request, Settings, Logout) — WooCommerce's own "Payment methods" item, absent from the design, is dropped from the menu (still reachable at its direct URL). The same class registers the theme's two custom endpoints (wishlist, sav) via add_rewrite_endpoint(); their real content is wired in later steps of this area's build-out.

woocommerce/myaccount/dashboard.php delegates to template-parts/account/dashboard.php a greeting, 4 stat cards (in-progress orders, total orders, wishlist, active support requests — computed by Solar_Template\Account\Dashboard from the customer's real orders), a recent orders table with a colored status badge (Solar_Template\Account\OrderStatusPresenter) and 3 quick links. An already-delivered order offers a "Reorder" link (Solar_Template\Account\ReorderHandler) that adds every item of that past order back into the cart in a single, nonce-protected request.

Technical decision: every menu label/order comes from this theme's own translation catalog rather than WooCommerce's own defaults (e.g. "Settings" rather than core's "Account details"), to stay faithful to the design's wording regardless of which core WooCommerce translation is installed. The "Wishlist"/"Support" stat counts start at 0 until those two features are themselves built, then get wired to their real data once ready.

Verified end to end in the real Docker environment with WooCommerce active (permalinks set to a non-"plain" structure, a WooCommerce requirement for its own endpoints): a test customer account with two real orders (one "in transit", one "delivered") shows exact stats and a recent orders table, the active navigation item matches every visited page, and the "Reorder" link genuinely adds the right items/quantities to the cart (confirmed via the real cart summary). No PHP warning or error observed.

Orders

woocommerce/myaccount/orders.php now shows status tabs (All, In progress, Delivered, Returns — with their real counts) and order cards (a status-colored header, item thumbnails, actions) instead of WooCommerce's default table, driven by a real ?orders-tab=... link — works without JavaScript, each tab being a plain link. Solar_Template\Account\OrdersView computes the tab counts and builds each order card from the customer's real orders.

woocommerce/myaccount/view-order.php restyles the page's own heading (order number, date, colored status badge) and the order note history, while keeping WooCommerce's native woocommerce_view_order hook untouched below it — that's what renders the real order details table, any download links and the "Order again" button, reused as-is rather than reimplemented.

Technical decision: the "Returns" tab only counts orders with WooCommerce's own "refunded" status (no native concept of a partial return distinct from that status); the design's own "Track my order" and "Download invoice" buttons are deliberately left out (no real carrier or PDF invoice generator exists in this theme) in favor of "View detail" and "Reorder", already real and functional.

Verified end to end in the real Docker environment with WooCommerce active: the "In progress"/"Delivered" tabs correctly isolate the right orders on the test account, an order's detail page shows the right number/status/item table, and the "Reorder" link keeps working from this list. No PHP warning or error observed.

Wishlist

The heart button already present on every product card (a shared design-system component) now genuinely toggles via AJAX (assets/js/account.js, initWishlistToggle(), delegated on document so it also covers cards added dynamically by the catalog) and persists in a dedicated wp_solar_template_wishlist table (Solar_Template\Account\WishlistRepository) — a logged-out visitor is sent to the login page rather than having the request fail silently.

Solar_Template\Catalog\ProductCardMapper::map() now computes each product card's real "saved" state from that table, for the logged-in customer. The account area's new "Wishlist" endpoint (Solar_Template\Account\WishlistController::render_wishlist_page()) shows a grid of saved products, reusing the existing product card component as-is.

Technical decision: this step only touches product cards (catalog, home page, related products) — the design's own wishlist button on the product page's panel, mentioned elsewhere in the handoff, stays out of this step's scope (its own wording only mentions "product cards").

Verified end to end in the real Docker environment with WooCommerce active: toggling a product from the shop grid persists its state (page reload, dashboard, "Wishlist" page), and removing it makes it disappear from that page (test product removed after verification). No PHP warning or error observed.

Addresses

woocommerce/myaccount/form-edit-address.php renders two summary cards (billing/ shipping, Solar_Template\Account\AddressesView) above the real edit form, whose fields are grouped into a 2-column grid by directly reusing the component already built for the sales tunnel (Solar_Template\Checkout\CheckoutFieldsLayout::rows(), purely structural — it only inspects field keys/order, never a checkout-specific shape).

Technical decision: this WooCommerce version no longer offers a separate address listing page — the "edit-address" endpoint always renders an edit form directly (billing by default), never an overview of both addresses side by side. The design's own "grid of cards, each linking to its own edit page" concept is adapted to this real behavior: both summary cards stay visible at all times, and the form below switches between billing/shipping depending on which card was clicked, rather than navigating to a listing page that no longer exists.

Bug found and fixed during Docker verification: the bare /my-account/edit-address/ URL (no billing/shipping segment) reaches this template with an empty address type on WooCommerce's own side (its own 'billing' default parameter never applies here, since the endpoint's URL always passes an explicit value, even an empty one) — the form's own fields then lost their billing_/shipping_ prefix. Fixed with an immediate redirect to the billing sub-page in that specific case, rather than attempting to render incorrectly-prefixed fields.

Verified end to end in the real Docker environment with WooCommerce active: a real billing form submission (test address) updates the account and immediately shows in its own summary card; the shipping form renders its own correctly-prefixed fields. Test data removed after verification. No PHP warning or error observed.

Downloads

woocommerce/myaccount/downloads.php shows the customer's real downloadable products (icon by extension, order reference, remaining download count or "Unlimited", download button) from WC()->customer->get_downloadable_products(), via Solar_Template\Account\DownloadsView — no fake data, and no file size shown (WooCommerce doesn't natively expose it for a remote file without risking a costly disk call on every page render).

Verified end to end in the real Docker environment with WooCommerce active: a test downloadable product purchased through a real order shows the right icon, order reference and remaining download count, and the download button genuinely serves the real file. Test product and order removed after verification. No PHP warning or error observed.
