Home page

front-page.php assembles the home page section by section, each one a self-contained template-part under template-parts/front-page/ — as each is built.

Hero

template-parts/front-page/hero.php renders the full-viewport hero (dark background, two-column grid): a gold eyebrow label, a three-line heading (the middle line in accent gold italics), a subtitle, two calls to action, a list of trust badges, and a media block with a floating "favorite pick" card (title, price, stock progress bar). Styled by assets/scss/_hero.scss, built entirely from the shared design tokens — see Design system.

All of its content (eyebrow, heading, CTAs, trust badges, floating card) comes from a single filterable helper, solar_template_hero_config() in functions.php — the same convention as solar_template_footer_config() and the other common-structure helpers. No real data (a featured product, an image) is wired in at this step: this is placeholder editorial content, ready for the future "Home page" administration tab to hook into.

Technical decision: both hero CTAs point at the WooCommerce shop page (solar_template_shop_url()), matching the mockup — there is no dedicated "new arrivals" view yet to point the second one at, for the same reason as the primary navigation (see Common structure).

Verified in the real Docker environment, in both installed languages (French and English): the section renders without any warning or error, fully translated according to the site's active language. The highlight card's price formatting is not locale-aware yet ("129,00 €" in both languages) — the same known, documented limitation as template-parts/product-card.php's identical placeholder helper, superseded by WooCommerce's own wc_price() once wired to a real product.

Featured products

template-parts/front-page/featured-products.php renders a masonry grid (4 columns, a purely visual vertical offset on the 2nd and 4th card) of the WooCommerce products actually marked "Featured" from the product edit screen (solar_template_get_featured_products() in functions.php, backed by wc_get_products(['featured' => true])), each rendered with the product card component already in place (see Design system) rather than new markup.

Unlike the hero, this section reads real WooCommerce data: image, price, struck-through price and discount percentage when the product is on sale (an "On Sale" badge) all come straight from the WC_Product object (solar_template_map_product_to_card_args()). The product card's color swatches stay empty at this step: no reliable color attribute data is wired in yet (planned for a later catalog/product page step).

Technical decision: the section does not render at all when no product is marked as featured (WooCommerce inactive, or none marked yet), rather than showing an empty grid — the same graceful-degradation logic used throughout the theme.

Bug avoided before it caused a translation regression: the "On Sale" badge was initially going to reuse the English source string "Sale", already used by the "Promotions" navigation link with a different French translation for the same English text — the theme's translation catalog does not distinguish strings by context yet. Fixed by using a distinct source string ("On Sale") for the badge.

Verified end to end in the real Docker environment with WooCommerce active: two test products (one on sale) created and marked as featured confirm correct rendering (price, struck-through price, computed discount percentage), and unmarking them as featured makes the whole section disappear — test products deleted after verification.

Categories

template-parts/front-page/categories.php renders an asymmetric grid (1.4fr 1fr 1fr, the first category spanning both rows) of real WooCommerce product categories (solar_template_get_home_categories() in functions.php, backed by get_terms('product_cat')), sorted by product count (the most populated first) rather than a manual order — WooCommerce has no native "featured category" concept. Each card links to the category's real archive page (get_term_link()) and shows its WooCommerce category image when it has one.

Technical decision: same graceful-degradation logic as the previous sections — the section does not render at all when there is no populated product category (WooCommerce inactive, or an empty store), rather than showing an empty grid. The numbers shown on each card (01, 02…) are just positional numbering, not real data.

Verified end to end in the real Docker environment with WooCommerce active: two test categories, each with one product, confirm correct rendering (name, link to the category archive), and deleting them makes the whole section disappear — test categories and products deleted after verification.

Brand story

template-parts/front-page/brand-story.php renders an editorial image with a floating stat highlight card ("10+ years of expertise", dark background, gold figure), a two-paragraph introduction, a row of three stats (happy customers, products available, average rating) and a call to action.

Same convention as the hero: all of its content comes from a single filterable helper, solar_template_brand_story_config() in functions.php — placeholder editorial content, no real data wired in at this step. The CTA button reuses solar_template_page_url_by_slug('about') (already used by the footer), falling back to the home page as long as no page with the "about" slug exists.

Verified in the real Docker environment, in both installed languages: the section renders without any warning or error, fully translated according to the site's active language.

Testimonials

template-parts/front-page/testimonials.php renders a grid of three customer testimonials (quote, star rating out of 5, author), the middle card shown in an inverted style (dark background, light text) via a positional CSS class (testimonials__item--inverted, applied to the second item in the loop), matching the mockup.

Content (quotes, ratings, authors) stays editorial, exposed through a single WordPress filter (solar_template_testimonials, via solar_template_get_testimonials() in functions.php) rather than a new custom post type — the project roadmap explicitly calls for a "simply defined" content source at this stage, without building a dedicated admin screen now.

Verified end to end in the real Docker environment, in both installed languages: the section renders without any warning or error, fully translated according to the site's active language, with the middle card correctly inverted.

Blog preview

template-parts/front-page/blog-preview.php renders the 3 latest actually published blog posts (solar_template_get_blog_preview_posts() in functions.php), reusing the blog card component already in place rather than new markup.

Unlike the hero and brand story, this section reads real WordPress data: featured image, primary category (shown as a badge), publication date, title, excerpt and author (with their Gravatar avatar) all come straight from the post (solar_template_map_post_to_card_args()). The reading time shown next to the date is estimated from the post's word count (solar_template_estimate_reading_time_minutes(), 200 words per minute, rounded up, minimum 1 minute) rather than entered manually.

Technical decision: same graceful-degradation logic as the other sections backed by real data — the section does not render at all when there is no published post.

Verified end to end in the real Docker environment, in both installed languages: a test post confirms correct rendering (title, localized date, translated reading time, category, author) — test post deleted after verification.

Newsletter

template-parts/front-page/newsletter.php renders a sign-up form (email + button) on a dark background, handled natively — no dependency on a third-party newsletter plugin, per the project's structuring decisions. Its content (eyebrow, heading, description, labels) stays editorial and filterable, via solar_template_newsletter_config() in functions.php.

A new dedicated table, wp_solar_template_newsletter_subscribers (unique email), and a storage class (Solar_Template\Newsletter\SubscriberRepository) handle subscription and de-duplication — direct $wpdb access, no Contracts interface, same convention as Solar_Template\Database\Installer: no third-party library is wrapped here.

The form is submitted via AJAX (assets/js/newsletter.js, initNewsletterForms()) to solar_template_handle_newsletter_subscription() in functions.php, an admin-ajax.php endpoint protected by a nonce (check_ajax_referer()). Feedback (success, already subscribed, invalid email, error) is shown in the form's .js-newsletter-feedback element, without a page reload.

Technical decision: the newsletter form already present in the footer (added in an earlier common-structure step, markup only) is not wired to this mechanism in this version — it stays out of scope for this step, which only covers the home page's own dedicated section. The targeting class (.js-newsletter-form) would make that wiring trivial for a future step, without building it now.

Verified end to end in the real Docker environment with an actual AJAX request (identical to the one the form would issue): a valid subscription is recorded and confirmed, a second subscription with the same email is rejected with the right message, an invalid address is rejected before any database write — all fully translated according to the site's active language; test subscription deleted after verification.
