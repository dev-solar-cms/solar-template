Static pages

The theme's remaining generic pages: a selectable "Legal Page" template (Terms & Conditions, Privacy Policy, Legal Notice, Cookies), a native contact page, and a plain fallback template for any other WordPress Page.

Legal page template

page-templates/legal-page.php is a selectable page template (chosen from the Page Attributes panel in the block editor, registered via the theme_page_templates filter). It renders a dark hero (the page's own real title and last-modified date), a tab strip linking the site's own C.G.V./Privacy Policy/Legal Notice/Cookies pages (whichever of those four exist — a missing one simply falls back to the site's front page instead of a broken link), and a sticky table of contents next to the page's real content.

The table of contents is auto-generated from the page's own <h2> headings: Solar_Template\Pages\LegalPageController::annotate_headings() adds a stable id attribute to every heading that doesn't already have one (an author-set id is always kept as-is), and returns the ordered list those anchors point to — a pure string transform with no WordPress dependency, unit tested directly (accented text, duplicate heading text, inline markup inside a heading).

Technical decision: rather than hardcoding French legal copy, each of the four legal pages is a real, independent WordPress Page the site owner writes and structures with real <h2> headings — the template only supplies the tabs/table of contents/typography around whatever content exists.

Contact page

page-contact.php is automatically matched by WordPress' own page template hierarchy for the page whose slug is contact — no manual template selection needed, same file-based convention as archive-product.php/ single-product.php. It renders a native contact form, a store details panel, a map placeholder, and the FAQ accordion.

The form itself is a plain (non-AJAX) POST, handled by Solar_Template\Pages\ContactController::maybe_handle_submission() — no third-party form plugin. Anti-spam is a WordPress nonce plus a hidden honeypot field: a real visitor never sees or fills it, so any submission with that field filled in is silently redirected to the same success state a legitimate visitor would see, without sending any mail — never tipping off a bot that its submission was rejected. Field validation (required fields, email format, RGPD consent) is a pure function with no WordPress dependency, unit tested directly. A valid submission emails the site admin via native wp_mail(), with the visitor's own address set as the Reply-To.

The store details panel (address, phone, email, hours, social links, guaranteed response time) comes from a single filterable array (Solar_Template\Pages\ContactInfo::config()), same editorial-placeholder convention as the home page's Hero/Brand story sections — a future administration screen is expected to hook into this filter with the site owner's real details. The "open now"/"closed now" indicator is real, though: computed from the configured weekly schedule against the actual current day/time, not a hardcoded value.

The map itself stays a placeholder (no Google Maps or other third-party mapping service wired in), per this page's own explicit scope.

FAQ accordion

The FAQ section on the contact page is a native <details>/ <summary> accordion — opens and closes correctly with both mouse and keyboard with no JavaScript at all, by design. Content (Solar_Template\Pages\Faq::heading()/items()) is a single filterable array, same convention as the home page's testimonials — no dedicated custom post type or admin screen for this step.

Generic page fallback

page.php is WordPress' default fallback template for any Page that doesn't use a more specific one — a plain title and content, replacing index.php as the fallback the theme previously used for pages.

Verified end to end in the real Docker environment: a Terms & Conditions page with several real <h2> sections showed the tab strip, an auto-generated table of contents with working anchors, and correct French translations resolved through the theme's own translation catalog; the contact page's form was submitted with a valid payload (real success state, admin notification email attempted through wp_mail()), an invalid payload (error state, no email sent) and a filled-in honeypot field (fake success state, no email sent) — all three confirmed. Test pages/content used for this verification were kept as the site's real starter content, since they are the actual pages the site now needs to exist.
