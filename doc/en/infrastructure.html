Infrastructure

Running commands against the local WordPress install

This theme only runs inside a WordPress installation. Locally, that installation is managed by the parent wordpress-dev-env Docker environment (make start, see that repository's own documentation). This repository does not ship wp-cli or Composer inside the container image — they are fetched on demand, as disposable .phar files, so nothing about the container image itself has to change: 

docker compose exec wordpress bash -lc "
  curl -sSL -o /tmp/wp-cli.phar https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar
  chmod +x /tmp/wp-cli.phar
  php /tmp/wp-cli.phar core version --path=/var/www/html --allow-root
"

The same approach is used for Composer:

docker compose exec wordpress bash -lc "
  curl -sSL -o /tmp/composer.phar https://getcomposer.org/composer-stable.phar
  chmod +x /tmp/composer.phar
  php /tmp/composer.phar --version
"

Both commands can also be run through make terminal once inside the container shell. Every functional check described on this page (activating the theme, inspecting the database, compiling translations, running the WooCommerce notice) was verified this way, against the real WordPress install.

PHP dependencies and contracts

The theme uses Composer for its PHP dependencies, autoloaded under the Solar_Template\ namespace (PSR-4, mapped to inc/). Business code never calls a third-party library directly: it depends on an interface defined under Solar_Template\Contracts\*, with a default implementation provided under Solar_Template\Support\* (or a dedicated namespace for larger subsystems, e.g. Solar_Template\I18n\*). This keeps every dependency replaceable without touching the code that consumes it. 

composer install   # install dependencies + generate the autoloader
composer lint      # check the coding standard (WordPress-Extra, via PHP_CodeSniffer)
composer format    # auto-fix what can be auto-fixed (phpcbf)

A fresh clone of this theme does not ship a vendor/ directory. The theme still activates without it — it shows an administration notice asking to run composer install instead of causing a fatal error.

Theme configuration (.env)

The theme reads its own non-sensitive settings (version, asset build mode, cache TTL) from a .env file at its root, copied from the versioned .env.example. It is entirely separate from the parent wordpress-dev-env repository's own .env: no shared variable names, and this theme never reads or stores database credentials — those stay with the parent repository.

Asset build pipeline

SCSS/JS sources live in assets/scss/ and assets/js/ and are compiled by Vite into assets/dist/main.css / assets/dist/main.js. 

npm install       # install dependencies
npm run build     # one-off production build (no sourcemaps)
npm run dev       # rebuild continuously (development, with sourcemaps)
npm run format    # auto-format assets/**/*.{js,scss} with Prettier

The theme enqueues the compiled files only if they exist, cache-busted with the file's own modification time — no build yet simply means no custom CSS/JS is loaded (plus an administration notice), never a fatal error.

Translation system

The theme's templates keep calling WordPress' own translation functions everywhere — __(), _e(), _n() — with the solar-template text domain, exactly like any other theme. What is custom is where the translated text comes from: instead of shipping hand-edited .po/.mo files, the theme stores every string in two database tables (wp_solar_template_languages, wp_solar_template_translations) editable from the theme's own administration screens (a later milestone), and compiles them into standard .mo files whenever they change. WordPress then loads those files the normal way — nothing about how templates read translations changes.

French (fr_FR) and English (en_US) are pre-installed; adding another language never requires touching the theme's code.

Solar_Template\I18n\DefaultStrings lists every user-visible string the theme's PHP code currently calls __()/_e()/_n() on, together with its French and English translation. Theme activation seeds the catalog from this list (see Database tables and activation) before compiling it, so every string always has a real translation row behind it — never just a text-domain call with nothing to back it. It grows by one entry every time a change introduces a new visible string; a future translation editor screen edits the same rows.

TablePurpose
wp_solar_template_languagesInstalled languages: code, label, flag, active/default
wp_solar_template_translationsCatalog: key → singular/plural text per language

Note: a theme's own languages/ directory expects `.mo` files named {locale}.mo (e.g. fr_FR.mo) — not {textdomain}-{locale}.mo, which is only required for the shared wp-content/languages/themes/ directory. This is what DatabaseTranslator::compile() writes.

Note: string_key/context (wp_solar_template_translations) are explicitly declared with a binary, case-sensitive collation (utf8mb4_bin) rather than the database's own default. A gettext msgid is case-sensitive by nature — the theme legitimately registers both "Orders" (a page title) and "orders" (an inline reference) as two distinct strings — but a default, case-insensitive MySQL collation collapsed such pairs under this table's unique key, silently discarding one of them on every activation. Installer::create_i18n_tables() corrects an already-created table's collation on every (re-)activation too, since `dbDelta()` does not reliably alter a column's collation on its own.

Solar_Template\Theme::setup() calls load_theme_textdomain() on after_setup_theme. Which locale WordPress actually loads for a given request is resolved by Solar_Template\Admin\TranslationsSettings::filter_locale() (hooked on the core determine_locale filter, front-end only — an administrator's own profile language in wp-admin is never overridden): the visitor's Accept-Language header is matched against the theme's active languages first (exact match, e.g. `fr-FR` → `fr_FR`, then same-primary-subtag, e.g. `fr` → the first active `fr_*` language) when automatic detection is enabled in the Translations tab, then the tab's own configured default language, then WordPress' own site language — a clean fallback chain with no error at any step: a locale with no matching (or not yet compiled) `.mo` file simply falls back to the original English source text, exactly like core WordPress does for any theme.

Compatibility with WPML/Polylang: since the theme only ever calls WordPress' own standard translation functions (__()/_e()/ _n(), text domain solar-template) and the core load_theme_textdomain()/determine_locale mechanisms, it works unmodified alongside WPML or Polylang: either plugin can filter determine_locale or swap in its own compiled translations the same way this theme's own TranslationsSettings::filter_locale() does, with no dependency on either plugin and no special-casing anywhere in the theme's code.

Two dedicated admin screens (see Administration → Translations tab) manage languages and translations without ever leaving wp-admin: a Languages page (search and add any of the theme's known standard languages — each with its classic locale code and flag — list the ones already added, set the default one, remove a non-default one) and a Translation Editor (every registered string, searchable and paginated, editable per language with placeholders like %s/%d shown explicitly and the plural form edited separately when a string uses _n()); saving recompiles that language's `.mo` immediately.

Automated tests

composer test   # PHP unit tests (PHPUnit)
npm run test    # JS unit tests (Vitest, jsdom)

The PHP suite runs with a minimal bootstrap (tests/php/bootstrap.php) that only defines the handful of WordPress functions/constants actually exercised outside of a real install (in-memory transients, ARRAY_A, …) — not a full WordPress core stub library. No warning or deprecation is tolerated in either suite. This automated suite complements, but never replaces, the manual functional check against the real Docker WordPress install performed for every change described on this page.

Continuous integration

Every push and pull request runs the PHP coding standard, the PHP test suite (on PHP 8.1 and 8.3), a production asset build, and the JS test suite. A successful push to main automatically creates a GitHub release for the current composer.json version (tagged vX.Y.Z), with that version's section of the project's release notes as its description — unless that version was already released.

Database tables and activation

On activation, the theme creates three dedicated tables (prefixed wp_solar_template_) and seeds each with minimal default data — never an empty table with nothing usable in it:

TablePurpose
wp_solar_template_languagesInstalled languages
wp_solar_template_translationsTranslation catalog
wp_solar_template_settingsGeneric key/value settings (theme version, base colors, logo/favicon)

This runs from a single idempotent Installer::install() call, hooked to WordPress' after_switch_theme: reactivating the theme, or activating it on a fresh database, never duplicates the default rows.

WooCommerce detection

The theme does not require WooCommerce to activate. Solar_Template\Support\WooCommerceStatus::is_active() (a thin wrapper around class_exists('WooCommerce')) is the single place the rest of the theme checks. When WooCommerce is missing or inactive, an administration notice is displayed inviting the site administrator to install/activate it, and add_theme_support('woocommerce') is only declared once it is actually active — never causing a fatal error either way.
