Administration

The theme's own settings screen, built directly into the theme via the WordPress Settings API rather than a separate plugin. A "Solar Template" top-level admin menu page renders a vertical tab layout (a nav column plus content, mirroring the design handoff's own admin chrome), with one form per tab.

Settings framework

Solar_Template\Admin\SettingsPage registers the admin menu, renders the shared chrome (header, save feedback notice) and dispatches each tab's own fields/sanitization to its Solar_Template\Admin\SettingsTabInterface implementation — adding a future tab only means implementing that interface and listing it in SettingsPage::tabs(), no other file changes. Fields are registered with the real register_setting()/add_settings_section()/ add_settings_field() Settings API primitives, same convention as any other WordPress options screen; actual persistence goes through Solar_Template\Admin\SettingsRepository, a plain key/value wrapper (dotted {tab}.{field} keys) around wp_solar_template_settings — the generic settings table already created (and seeded with a few of these exact keys) back when the project's database tables were first laid out, anticipating this screen.

General tab

Shop name (falls back to the site's own title when empty — used by the header brand and, via the wp_mail_from_name filter, transactional email), logo/favicon through WordPress' native media uploader, currency and symbol position (applied to WooCommerce itself through the generic pre_option_woocommerce_currency/ ..._currency_pos filters when configured, left alone otherwise), and maintenance mode. Solar_Template\Admin\MaintenanceMode renders a real minimal 503 page to anyone who isn't a signed-in administrator while it's on — administrators keep browsing the real site to check their changes.

Appearance tab

Primary/accent/background colors (with clickable preset swatches), main/heading Google Fonts, and a single "element roundness" preset (Square/Subtle/Rounded/Pill). These apply to the real front end without rebuilding the compiled assets: assets/scss/_tokens.scss's own color/radius/font-family tokens are now defined as var(--solar-*, <compiled default>) instead of a plain Sass value — a one-line change per token that every one of its usages across the whole compiled stylesheet automatically inherits, since Sass just substitutes the token's string value everywhere it's referenced. Solar_Template\Admin\AppearanceSettings::print_style_overrides() then prints the real, saved values as `:root` custom properties in `wp_head`, after the compiled stylesheet, and enqueue_google_fonts() loads the chosen font families. A couple of hardcoded Sass color functions (color.adjust(), which needs a real compile-time color and can't operate on a `var()` expression) were converted to the equivalent plain CSS color-mix() calls, for the same reason. Derived gold hover/ light shades stay static — following a fully custom accent color's own tint would need runtime color math, out of scope for this pass.

Header tab

Layout (3 real CSS variants — the default centered one unchanged, "left logo, centered nav" and "left logo, right nav" reorder the same header markup via modifier classes and the `order` CSS property, no markup change), mega menu toggle (hooked onto the `solar_template_header_mega_menu_enabled` filter Group 02 already left for this), a promo bar, 4 social network URLs (hooked onto the existing `solar_template_social_links` filter — Pinterest is now a 4th default network alongside Instagram/Facebook/X), and a transparent-on-home option. The transparent header overlaps the hero instead of pushing it down, until assets/js/header.js's initTransparentHeader() adds a `--scrolled` class past a small scroll threshold, restoring the normal sticky/opaque header — without it, text would become illegible once the visitor scrolls past the dark hero.

Footer tab

Column count (2–5; the brand column, and the newsletter column when enabled, each reserve one slot, the rest go to Shop/Information/Legal in that order — a pure, unit-tested FooterSettings::resolve_visible_columns() trims the list), the newsletter column toggle, payment method badges (Visa/Mastercard/PayPal/Stripe/Apple Pay/Google Pay), and the copyright text (`{year}` support already existed from Group 02). All four hook onto the filters (`solar_template_footer_config`/`..._payment_icons`/`..._copyright`) already left there for this purpose.

Home page tab

A list of front-page.php's seven sections (Hero, Featured products, Categories, Our story, Testimonials, Blog, Newsletter), reorderable via native HTML5 drag & drop (no library) with an enable/disable checkbox per section. Order and visibility are two comma-separated slug lists (home.sections_order/ home.sections_enabled), resolved by a pure, unit-tested function, Solar_Template\Admin\HomeSettings::resolve_order() (any known slug missing from the submitted list is appended at the end, never silently dropped). front-page.php now loops over HomeSettings::visible_sections() instead of a fixed list of get_template_part() calls: reordering or unticking a section here genuinely changes what renders, and in what order.

Products tab

Columns and products per page (hooked onto the existing solar_template_catalog_columns/loop_shop_per_page filters). Filter bar position — Top / Sidebar left / Sidebar right: the same template-parts/catalog-filters.php bar (Category/Price/Color/Size/Rating) just switches from a horizontal to a vertical layout depending on Solar_Template\Catalog\CatalogOptions::filters_position(), no code duplication. An independent sidebar of widgets can also be enabled, regardless of that position setting: Solar_Template\Catalog\CatalogSidebar and template-parts/catalog-sidebar-widgets.php offer Category/Price/Color/Brand/ Rating as plain links (not a second `<form>`, so it never clobbers whatever filters the page's other form already has active), reusing the exact same query mechanism as the bar (CatalogFilters::url()/remove_url()). "Brand" is a genuinely new filter dimension — a filterable attribute taxonomy, same as Color/Size (CatalogOptions::brand_attribute_slug(), `pa_brand` by default), not a decorative label. Related products: enable/disable and how many to show, hooked onto Solar_Template\Product\ProductRelated::products(). Custom engraving: a site-wide toggle, section label, field type (single vs. multiple lines), and default surcharge — all new filters on Solar_Template\Product\ProductEngraving (solar_template_engraving_*); a product's own toggle (Group 05) is still required on top of this site-wide one for that product to actually offer it.

Blog tab

Articles per page (applied to the index/category/tag archive main query via pre_get_posts), the featured-article block toggle, grid columns, share buttons (Facebook/X/Pinterest as real links to those networks, plus "Copy link" reusing the existing native Web Share/clipboard button — Solar_Template\Blog\ArticleShare), and the number of related articles (0 hides that section entirely). Disabling the featured block doesn't make the sticky post disappear: it goes back to being a plain grid post like any other — a bug found during this step's own Docker verification (WordPress still re-inserted the sticky post ahead of the configured per-page count unless ignore_sticky_posts was explicitly set in that case) was fixed in Solar_Template\Blog\BlogController::exclude_featured_post().

Translations tab

Default language and automatic detection, genuinely applied to the front-end visitor (and only there — never in wp-admin) through WordPress' own determine_locale filter. Solar_Template\Admin\TranslationsSettings::resolve_locale() and match_accept_language() are pure, unit-tested functions matching the browser's own Accept-Language header against the theme's active languages (Solar_Template\I18n\Translator) — an exact match first (`fr-FR` → `fr_FR`), then a same-primary-subtag one (`fr` → the first active `fr_*` language), before falling back to the configured default language and then the site's own language. This tab also lists every active language with a download link for its already-compiled `.mo`, and a drag & drop zone to import a `.po`/`.mo` file (the `gettext/gettext` library, already a dependency) into the same catalog the two screens below edit directly.

A "Manage languages →" button opens the Languages page (Solar_Template\Admin\LanguagesController): a searchable list of the theme's known standard languages (Solar_Template\I18n\LanguageCatalog — each with its classic locale code and flag, no language ever hardcoded in a template), an "Add" action per language, the list of languages already added with a "Set as default"/"Remove" action for each (removing the current default is refused — a new one must be chosen first). A "Translate strings →" button opens the Translation Editor (Solar_Template\Admin\TranslationsEditorController): every string the theme's code currently registers (Solar_Template\I18n\DefaultStrings), searchable and paginated (Solar_Template\Admin\TranslationCatalog::build_rows(), a pure, unit-tested function), editable per language with every %s/%d/ %1$s-style placeholder highlighted and called out explicitly, and the plural form edited as its own field whenever a string uses _n(). Saving writes straight to the catalog and recompiles that language's `.mo`, so the change is live on the front end immediately — see Infrastructure → Translation system for how the underlying catalog/locale-detection/`.mo` mechanism works, and for the note on this theme's WPML/Polylang compatibility.

Cache & asset regeneration

A button at the bottom of the General tab (Solar_Template\Admin\CacheRegenerator, AJAX action solar_template_regenerate_cache) purges the theme's own cache (Solar_Template\Support\TransientCache, behind the Contracts\CacheInterface — see Infrastructure → Performance & caching for what it actually stores), WordPress' object cache and PHP's opcode cache when available, then reruns `npm run build` when Node tooling is actually present server-side (which also regenerates the inlined critical stylesheet — same page) — this Docker container ships PHP only, so that last step reports itself skipped there instead of silently failing. Each step's result renders under the button with no page reload.

Verified end to end in the real Docker environment: every field re-reads correctly after a real save (nonce included), every setting visibly changes the real front end (colors/fonts/ roundness, header layout/promo/social/transparency, footer columns/newsletter/payment/ copyright, WooCommerce's own displayed currency, home page section order/visibility, catalog layout and sidebar widgets, custom engraving, blog pagination/featured/columns/share/related), and maintenance mode returns a real 503 to a logged-out visitor while an administrator keeps browsing normally. No PHP warning or error observed.
