Administration

The theme's own settings screen, built directly into the theme via the WordPress Settings API rather than a separate plugin. A "Solar Template" top-level admin menu page renders a vertical tab layout (a nav column plus content, mirroring the design handoff's own admin chrome), with one form per tab.

Settings framework

Solar_Template\Admin\SettingsPage registers the admin menu, renders the shared chrome (header, save feedback notice) and dispatches each tab's own fields/sanitization to its Solar_Template\Admin\SettingsTabInterface implementation — adding a future tab only means implementing that interface and listing it in SettingsPage::tabs(), no other file changes. Fields are registered with the real register_setting()/add_settings_section()/ add_settings_field() Settings API primitives, same convention as any other WordPress options screen; actual persistence goes through Solar_Template\Admin\SettingsRepository, a plain key/value wrapper (dotted {tab}.{field} keys) around wp_solar_template_settings — the generic settings table already created (and seeded with a few of these exact keys) back when the project's database tables were first laid out, anticipating this screen.

General tab

Shop name (falls back to the site's own title when empty — used by the header brand and, via the wp_mail_from_name filter, transactional email), logo/favicon through WordPress' native media uploader, currency and symbol position (applied to WooCommerce itself through the generic pre_option_woocommerce_currency/ ..._currency_pos filters when configured, left alone otherwise), and maintenance mode. Solar_Template\Admin\MaintenanceMode renders a real minimal 503 page to anyone who isn't a signed-in administrator while it's on — administrators keep browsing the real site to check their changes.

Appearance tab

Primary/accent/background colors (with clickable preset swatches), main/heading Google Fonts, and a single "element roundness" preset (Square/Subtle/Rounded/Pill). These apply to the real front end without rebuilding the compiled assets: assets/scss/_tokens.scss's own color/radius/font-family tokens are now defined as var(--solar-*, <compiled default>) instead of a plain Sass value — a one-line change per token that every one of its usages across the whole compiled stylesheet automatically inherits, since Sass just substitutes the token's string value everywhere it's referenced. Solar_Template\Admin\AppearanceSettings::print_style_overrides() then prints the real, saved values as `:root` custom properties in `wp_head`, after the compiled stylesheet, and enqueue_google_fonts() loads the chosen font families. A couple of hardcoded Sass color functions (color.adjust(), which needs a real compile-time color and can't operate on a `var()` expression) were converted to the equivalent plain CSS color-mix() calls, for the same reason. Derived gold hover/ light shades stay static — following a fully custom accent color's own tint would need runtime color math, out of scope for this pass.

Header tab

Layout (3 real CSS variants — the default centered one unchanged, "left logo, centered nav" and "left logo, right nav" reorder the same header markup via modifier classes and the `order` CSS property, no markup change), mega menu toggle (hooked onto the `solar_template_header_mega_menu_enabled` filter Group 02 already left for this), a promo bar, 4 social network URLs (hooked onto the existing `solar_template_social_links` filter — Pinterest is now a 4th default network alongside Instagram/Facebook/X), and a transparent-on-home option. The transparent header overlaps the hero instead of pushing it down, until assets/js/header.js's initTransparentHeader() adds a `--scrolled` class past a small scroll threshold, restoring the normal sticky/opaque header — without it, text would become illegible once the visitor scrolls past the dark hero.

Footer tab

Column count (2–5; the brand column, and the newsletter column when enabled, each reserve one slot, the rest go to Shop/Information/Legal in that order — a pure, unit-tested FooterSettings::resolve_visible_columns() trims the list), the newsletter column toggle, payment method badges (Visa/Mastercard/PayPal/Stripe/Apple Pay/Google Pay), and the copyright text (`{year}` support already existed from Group 02). All four hook onto the filters (`solar_template_footer_config`/`..._payment_icons`/`..._copyright`) already left there for this purpose.

Verified end to end in the real Docker environment: every field re-reads correctly after a real save (nonce included), every setting visibly changes the real front end (colors/fonts/ roundness, header layout/promo/social/transparency, footer columns/newsletter/payment/ copyright, WooCommerce's own displayed currency), and maintenance mode returns a real 503 to a logged-out visitor while an administrator keeps browsing normally. No PHP warning or error observed. The Home page/Products/Blog/Translations tabs and the cache/build regeneration button remain for a future pass.
