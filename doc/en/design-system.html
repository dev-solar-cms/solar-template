Design system

The theme's visual language — colors, typography, spacing, geometry, and the reusable components built from them — lives entirely in SCSS partials under assets/scss/, imported by the single entry point (assets/scss/main.scss). No component partial hardcodes a raw value already covered by a token.

Design tokens

Every color, typography, spacing and geometry value from the design is defined once in assets/scss/_tokens.scss, as plain SCSS variables plus a set of mixins that bundle each row of the typographic scale (type-display, type-h1, type-h2, type-h3, type-body, type-small, type-caption, type-price).

CategoryExamples
Colors$color-bg, $color-dark, $color-gold, $color-gold-dark, $color-muted, $color-border, $color-success, $color-error, $color-sale…
Typography$font-family-base (Plus Jakarta Sans), font-weight scale (300–800), fluid clamp() sizes for each scale step (display, h1–h3, body, small, caption, price)
Spacing$container-max-width (1440px), $container-padding-x, $spacing-section-y, $spacing-card-gap, product/blog grid gaps
Geometry$radius-card, $radius-content-card, $radius-modal, $radius-button, $radius-pill, $radius-input, card hover/admin box-shadows

Ranges given by the design handoff as a min–max pair (e.g. "56–80px" for the display size) are reproduced with a fluid clamp() expression rather than a single fixed value, so type actually scales with the viewport instead of jumping at a single breakpoint. A range given for a border-radius (e.g. "8–10px" for content cards vs. modals) is instead split into two separate tokens ($radius-content-card: 8px, $radius-modal: 10px), since that range described two different components rather than a single fluid value.

The theme loads Plus Jakarta Sans (weights 300 to 800) from Google Fonts, enqueued in functions.php alongside the compiled stylesheet.

Buttons, badges and pills

The base interactive components, defined in assets/scss/_buttons.scss, _badges.scss and _pills.scss, all built from the tokens above.

ComponentClassesUse
Buttons.btn, .btn--primary, .btn--dark, .btn--outline, .btn--outline-on-dark, .btn--lg, .btn--blockPrimary gold CTA, dark full-width CTA, outline on a light or dark background, large/full-width modifiers
Badges.badge--new, .badge--exclusive, .badge--sale, .badge--outline-gold, .badge--discountProduct card corner badges and the price discount badge (tinted background, not a solid fill)
Pills.pill, .pill.is-active, .pill__removeFilter chips and category pills, with an optional inline "×" remove button

A handful of values used only by a component's own chrome (e.g. a button's 13.5px label size) are not part of the content typographic scale, so they are declared as local SCSS variables at the top of that component's partial instead of in _tokens.scss — every color and geometry value they use still comes from the shared tokens.

No live WordPress page renders these components yet (header.php/ footer.php and every page template are still to come). Conformance with the design handoff is instead verified by test/js/design-system.test.js, which compiles the SCSS directly and asserts on the generated CSS (colors, radii, hover/active states) for every variant.

Product card

template-parts/product-card.php renders a single product card (image, corner badge, wishlist button, "add to cart" hover overlay, category, name, price with an optional struck-through original price and discount badge, color swatches) from a plain $args array, styled by assets/scss/_product-card.scss.

$args is deliberately shaped like WooCommerce product data (name/price/regular_price/ currency_symbol…) even though this step only renders fake data — no WC_Product is read yet. The price is formatted by a small local helper, expected to be replaced by WooCommerce's own wc_price() once the card is wired to real products (catalog grid, "similar products" section). The helper function is declared behind a function_exists() guard so the template-part can be included once per product in a loop without a fatal error on redeclaration.

Every string the card itself outputs ("Add to wishlist", "Add to cart", the "−XX%" discount label) is registered in the translation catalog for French and English via Solar_Template\I18n\DefaultStrings — see Translation system. A badge's own label (e.g. "New") is supplied by whichever template calls this card, not hardcoded here.

Verified against a real WordPress install: get_template_part() renders the card correctly with fake data, and switching the active locale to fr_FR correctly translates every string the card owns through the compiled .mo file — confirming the whole chain (catalog → compiled file → WordPress' own gettext loading → template output) end to end, not just the card's markup in isolation.

Blog post card

template-parts/blog-card.php renders a single blog post card (16:10 image, category badge, meta line, title, excerpt clamped to three lines, author) from a plain $args array, styled by assets/scss/_blog-card.scss. Like the product card, it is shaped like WordPress post data on purpose but does not read a WP_Post yet.

The meta line (date + reading time, e.g. "Jan 12, 2026 · 5 min read") is accepted as a single pre-formatted string rather than separate fields: the exact wording of that combination is a content decision for whichever template composes it, and — once wired to real posts — the reading-time part will need its own translatable, plural-aware format string. Inventing that string now, without a real post/reading-time source to drive it, was judged out of scope for a step that only renders this card with fake data.

This card introduces no string of its own: every piece of text it renders (title, excerpt, meta, author name, badge label) is supplied by whichever template calls it, so there is nothing new to register in the translation catalog for this component.
