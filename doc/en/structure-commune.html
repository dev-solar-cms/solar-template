Common structure

The template files shared across every page of the theme — header (header.php), footer, navigation, search and cart — documented as they are built.

Sticky header

header.php opens the document and renders the theme's header: a top bar (social links, site brand, search/account/cart icons) and a primary navigation bar, both made sticky (position: sticky) via assets/scss/_header.scss, built entirely from the shared design tokens — see Design system.

The primary navigation is powered by wp_nav_menu() on the primary location: a site administrator can assign it a custom menu from Appearance > Menus. Until a menu is assigned there, solar_template_primary_nav_fallback() (in functions.php) renders the design's default items (Shop, New In, Collections, Sale, Blog, Contact), each pointing at the closest equivalent already available in a stock WordPress/WooCommerce install (the WooCommerce shop/cart/account page, the posts page, a page whose slug is "contact" if one exists) rather than a dedicated view — those views (filtered archives, a real contact page…) are built by later steps of the project roadmap.

The account and cart icons point at the real WooCommerce pages (wc_get_page_permalink()) when WooCommerce is active, degrading gracefully to the WordPress login screen / the site's front page otherwise — consistent with the centralized detection already in place (Infrastructure — WooCommerce).

The cart badge (template-parts/cart-badge.php) is always present in the DOM, even at zero items (visually hidden via an is-hidden CSS class rather than omitted from the markup): a future AJAX cart refresh (woocommerce_add_to_cart_fragments) needs to be able to target that exact element instead of having to insert it into the DOM itself.

The social network URLs shown in the top bar come from a WordPress filter (solar_template_social_links), with a generic placeholder link for each network by default: there is no administration screen to configure them yet (planned for the "Header" tab of Group 10 of the roadmap), so the filter is the intended extension point for that future screen.

The top bar's search button only toggles its aria-expanded state at this stage (assets/js/header.js) — the search overlay itself is added by a later step of the common structure.

"Collections" mega menu

The primary navigation's "Collections" item opens a dropdown panel (template-parts/mega-menu.php, styled by the same _header.scss sheet) on mouse hover, on keyboard focus (Tab), and closes on Escape (returning focus to the link) or on a click outside the navigation — fully handled by assets/js/header.js (initMegaMenu()), with no console error in any of those cases.

The panel's content (link columns) is placeholder text, exposed through the solar_template_mega_menu_columns filter: wiring it to real WooCommerce categories is explicitly out of scope for this step (planned for a later catalog step) — the filter is the intended extension point for that future wiring. The mega menu can be disabled entirely via the solar_template_header_mega_menu_enabled filter, ahead of the "Header" tab of Group 10.

Technical decision: a site administrator can assign their own menu to the primary location from Appearance > Menus, but wp_nav_menu() does not natively apply the theme's own CSS classes to each item. Two WordPress filters (nav_menu_css_class, nav_menu_link_attributes) therefore apply the same classes the fallback navigation uses to any real menu assigned to that location — an administrator flags an item for the mega menu the same way the fallback does, by adding the has-mega-menu CSS class to it from the Menus screen. Verified in the real Docker environment with a test menu assigned to the primary location, including an item flagged has-mega-menu.

Bug caught and fixed during automated testing before it could affect a real user: closing the mega menu with Escape returned focus to the trigger link, which immediately fired its own focus-opens-the-menu handler, reopening the panel that had just been closed — fixed with a temporary guard that ignores that specific focus event while the programmatic refocus happens.

Footer

footer.php renders a five-column grid (Brand, Shop, Information, Legal, Newsletter) followed by a bottom bar (copyright, payment method badges), styled by assets/scss/_footer.scss and fed by three filterable helpers in functions.php: solar_template_footer_config() (brand, link columns, newsletter copy), solar_template_footer_payment_icons() and solar_template_footer_copyright().

The Shop/Information links resolve to the closest existing equivalent already available (the WooCommerce shop page, the posts page), same as the primary navigation. The Legal links (terms, privacy, legal notice, cookies) and "About" use solar_template_page_url_by_slug() — a helper extracted from the navigation logic at this step so both share it — which resolves to a page of the same slug if one exists, or the front page otherwise: those legal pages themselves are still to be built.

The newsletter form is accessible markup only (an email field with an associated label, a submit button with an accessible label): no sign-up logic is wired at this step, explicitly out of scope.

The copyright line uses a literal {year} placeholder, replaced by the current year at render time (not at translation time), so it never goes stale without intervention.

Verified in the real Docker environment: the footer renders without any warning or error on both the home page and the shop page, with the site name and current year correctly interpolated.

Search (overlay)

The top bar's search icon opens a full-screen overlay (#site-search, in header.php) wrapping searchform.php — the template WordPress' own get_search_form() automatically loads to customize its markup. The submitted search stays a native WordPress search (?s=): WordPress already includes every public, searchable content type — including WooCommerce products once the plugin is active — in a native search's results, with no extra wiring; an advanced search like SearchWP is explicitly out of scope.

Open/close is handled by initSearchOverlay() (assets/js/header.js): the top bar's button opens the overlay and moves focus into the search field; the close button, Escape, or a click outside the overlay close it and return focus to the trigger button — the same accessibility pattern as the mega menu.

Verified in the real Docker environment: a test blog post and a test WooCommerce product created for the occasion both appear in the results of the same search (?s=), confirming the native search actually surfaces relevant WordPress and WooCommerce content — test content removed after verification.

Dynamic cart count

The cart badge updates without a page reload through WooCommerce's own native "cart fragments" mechanism. solar_template_cart_fragments() (hooked to the woocommerce_add_to_cart_fragments filter in functions.php) returns exactly the same markup as template-parts/cart-badge.php, targeted by the span.site-header__cart-count selector — it is precisely because that badge is always present in the DOM since the header step (even hidden at zero items) that this mechanism can replace it.

Technical decision: no theme-specific JavaScript was written for the refresh itself — WooCommerce's own wc-cart-fragments script already listens for the added_to_cart event and replaces any DOM element matching a fragment's selector. The one missing piece, found by reading WooCommerce's own source (WC_Frontend_Scripts::load_scripts()): that script is only auto-enqueued by WooCommerce's native "Cart" widget, which this theme does not use (the header's cart icon is custom markup) — so it is enqueued explicitly by solar_template_enqueue_cart_fragments().

Verified end to end in the real Docker environment, without going through a browser UI (the product catalog itself is still to be built): an AJAX add-to-cart request identical to the one WooCommerce's own script sends (?wc-ajax=add_to_cart) was simulated against a test product — the response includes the span.site-header__cart-count fragment with the up-to-date count, and a full page reload with the same session confirms the rendered badge reflects that same count directly (initially hidden, then visible once an item is added) — test product removed after verification.

Verified in the real Docker environment with WooCommerce active: the theme activates without any header-related warning or error, the account/cart icons resolve to the install's real WooCommerce pages, and the fallback navigation renders correctly when no menu is assigned.
