Product catalog

archive-product.php renders the product catalog: the shop page, but also product category/tag archives, since WooCommerce automatically loads this same template as long as no dedicated taxonomy-product_cat.php/taxonomy-product_tag.php exists.

Product grid

The breadcrumb and page title reuse WooCommerce's own native functions (woocommerce_breadcrumb(), woocommerce_page_title()) instead of rebuilding a custom version: they already adapt correctly to the shop, a category or a tag with no extra code. The subtitle shows the number of products actually found by the current WooCommerce query (solar_template_catalog_result_count_label() in functions.php, correct singular/plural).

The grid reuses the standard WordPress/WooCommerce loop (have_posts()/the_post()/wc_get_product()) and the product card component already in place, mapped from a real WC_Product (solar_template_map_product_to_card_args(), already used by the home page's "Featured products" section). The column count is configurable (solar_template_catalog_columns(), solar_template_catalog_columns filter, clamped between 2 and 6), ready for the future "Products" administration tab.

Technical decision: the grid keeps the design handoff's masonry vertical offset (positional top margins on certain cards, unrelated to their content), only for the default 4-column layout. The quick category tag row and the grid/list toggle button shown in the mockup are deliberately not built here: the former is absorbed by the filter bar's own "Category" filter (see below), the latter has no behaviour specified beyond the mockup itself.

Defect identified and fixed: with real, variable-length product names, this positional masonry offset alone was no longer enough to keep cards aligned with each other — a name longer than its neighbours' made that card's total height vary, throwing the whole row out of alignment. Fixed in assets/scss/_product-card.scss by clamping the product name to a fixed two-line height (truncated with an ellipsis beyond that) and reserving a consistent minimum height for the card's text block whether or not its category is set — the product card being a shared component, this fix applies everywhere it is used.

Verified end to end in the real Docker environment with WooCommerce active: nine test products spread across three categories confirm the grid, breadcrumb, title and result count (singular and plural) on the shop page and on a category archive, in both installed languages; a category with no product confirms the translated empty-state message. One additional test product, with a deliberately very long name and no category, confirms that the grid's cards stay perfectly aligned with each other (at 4, 2, and 1 column depending on screen width) and that this name is correctly truncated with an ellipsis rather than breaking the layout; test product deleted after verification. No PHP warning or error observed.

Filter bar

template-parts/catalog-filters.php renders a sticky bar of five filters (Category, Price, Color, Size, Rating) as a plain native <form method="get"> — functional with JavaScript disabled, submitting a normal page load that solar_template_apply_catalog_filters_to_main_query() already filters (see functions.php) — then progressively enhanced into AJAX by assets/js/catalog.js (initCatalogFilters()): any checked box or changed price value submits the form to the solar_template_catalog_filter AJAX action, whose response replaces only the results area.

Each filter group only renders when it actually has an option to offer (same graceful-degradation convention as the rest of the theme): no "Color"/"Size" filter until the store has a matching global attribute — whose exact taxonomy name (pa_color/pa_size by default) is itself filterable (solar_template_catalog_color_attribute_slug()/ solar_template_catalog_size_attribute_slug()), since a store may have named that attribute differently. "Rating" has fixed options (5 down to 1 star(s)), always offered.

Technical decision: the "Category" filter fully replaces the current archive's taxonomy scope rather than narrowing it further — picking a category from the filter bar can move a visitor already on one category's archive to a different category entirely, exactly like the mockup's own category tag row would have. "Rating" reuses the real product_visibility "rated-N" taxonomy terms WooCommerce's own native rating widget filters on (wc_get_product_visibility_term_ids()) rather than a comparison on the stored average rating meta, to stay faithful to how WooCommerce actually buckets ratings.

Bug encountered and fixed during development: an early version built its own price filter on top of WooCommerce's own native price filter (which triggers automatically whenever min_price/max_price are present in the URL) — redundant, and the native one turned out broken for test products created directly in the database (its price lookup cache table was never synced, unlike a product saved normally from the admin). Fixed by re-syncing the test products and keeping a simple, self-contained price filter (a plain price comparison) that behaves identically whether the request is a normal page load or the AJAX request.

Verified end to end in the real Docker environment with WooCommerce active: every filter (alone and combined with others) confirmed through both a plain page load and the AJAX request, with identical results either way; checkbox checked state and the bar's active button styling stay in sync with the URL after a page reload. No PHP warning or error observed.

Active filters

template-parts/catalog-active-filters.php renders, below the filter bar, a row of chips summarizing each actively filtered value (category/color/size name, rating, or the whole price range — a single chip rather than two, since one control removes it) — an individual remove button on each chip, plus a "Clear all" link. Always rendered inside its own #catalog-active-filters container, even when empty, so assets/js/catalog.js can always replace it wholesale after an AJAX update without having to handle inserting/removing it separately.

Each chip and the "Clear all" link are plain links first (solar_template_catalog_filter_remove_url()/ solar_template_catalog_clear_filters_url() in functions.php) — functional without JavaScript, since the plain page load is already filtered server-side — then intercepted by assets/js/catalog.js: the target URL's query string is applied directly onto the filter bar's own controls (checkboxes checked/ unchecked, price fields updated), before submitting the form via AJAX instead of navigating.

Technical decision: chip URLs must be built relative to the real catalog page, not admin-ajax.php (the current request's URL during an AJAX call) — the client page therefore sends its own URL (window.location.href) along with the AJAX request, which the endpoint reuses as the base instead of the current request URL.

Bug encountered and fixed during development: an event listener accumulation was caught by the JS test suite (a scenario where initCatalogFilters() would run more than once on the same page triggered a growing number of AJAX requests per click). Fixed by explicitly tracking and removing the two listeners bound to the document before re-attaching new ones on every call, instead of letting them accumulate.

Verified end to end in the real Docker environment with WooCommerce active: chips correctly reflect each active filter (including the price range, natively formatted via wc_price()), their remove link removes only the matching value while keeping every other active filter, and "Clear all" removes everything — verified through both a plain page load and the AJAX request (base URL correctly based on the real catalog page either way), in both installed languages. No PHP warning or error observed.

Sorting

A plain native <select>, at the end of the filter bar, offers five options (Relevance, Price: low to high, Price: high to low, Newest, Best sellers) — solar_template_get_catalog_sort_options() in functions.php. Sorting is part of the same form and follows exactly the same path (plain page load already sorted server-side, enhanced into AJAX) as the filters themselves; it is preserved (not reset) when an active filter chip is removed.

Technical decision: every sort option maps to plain, real WP_Query args (solar_template_catalog_sort_query_args()) rather than relying on WooCommerce's own native sorting (WC_Query::get_catalog_ordering_args()) — "Price" and "Best sellers" use orderby=meta_value_num directly against real WooCommerce meta (_price, total_sales), a native WP_Query capability that needs no extra hook.

Bug encountered and fixed during development: "Best sellers" sorted correctly through the AJAX request but incorrectly on a plain page load. Cause: WooCommerce's own native sorting reads the URL's orderby parameter directly — the exact same name this used at first — and uses it to register its own ordering filter as a side effect, silently overriding the intended sort for the options where WooCommerce orders through a join against its own cache table rather than the meta directly. Fixed by using a dedicated URL parameter (catalog_orderby), unrelated to WooCommerce's own, removing the interference at the source rather than trying to work around it.

Verified end to end in the real Docker environment with WooCommerce active, with varied test prices and sales counts: every sort option (alone and combined with a category filter) confirmed with the same result through both a plain page load and the AJAX request, in both installed languages. No PHP warning or error observed.

Progressive loading

template-parts/catalog-load-more.php replaces numbered pagination with a "Showing N of M products" status, a gold progress bar (width = the real percentage loaded so far) and a "Load more products" button — a real link to the next page first (works without JavaScript, though a click without it then shows only that next page rather than adding it to the previous one, since appending without replacing needs JavaScript by nature), intercepted by assets/js/catalog.js to append that page's cards to the existing grid via AJAX instead of navigating.

Technical decision: the next-page AJAX request reuses the same endpoint as the rest of the filter bar (solar_template_catalog_filter), with a mode=append parameter that makes it respond with only the new cards (template-parts/catalog-cards.php, a cards-only loop extracted out of catalog-results.php so it can be reused without the grid wrapping it) and the updated progress block, rather than the whole results — consistent with the state already rendered client-side, which must not be overwritten.

Bug encountered and fixed during development: the number of products per page could differ between a plain page load (16 by default, implicitly derived by WooCommerce) and the AJAX request for the next page (10, WordPress's own generic setting — WooCommerce does not reliably apply its own default to a query built programmatically rather than through a real page visit), causing overlapping products between the two. Fixed by computing that number explicitly, the same way, in both cases, instead of depending on implicit behaviour that does not reliably apply outside of a real page request.

Verified end to end in the real Docker environment with WooCommerce active and nineteen test products (exceeding the default page size): the status, progress bar and button correctly reflect the real state on the first page; clicking correctly appends the remaining products with no duplicate or missing product, and the button disappears once everything is shown; combined with a category filter that brings the count below the page size, the whole block does not render at all. No PHP warning or error observed.
