Infrastructure

Exécuter des commandes contre l'installation WordPress locale

Ce thème ne tourne qu'à l'intérieur d'une installation WordPress. En local, cette installation est gérée par l'environnement Docker du dépôt parent wordpress-dev-env (make start, voir la documentation de ce dépôt). Ce dépôt n'embarque pas wp-cli ni Composer dans l'image du conteneur : ils sont récupérés à la demande, sous forme de fichiers .phar jetables, pour ne rien changer à l'image du conteneur elle-même : 

docker compose exec wordpress bash -lc "
  curl -sSL -o /tmp/wp-cli.phar https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar
  chmod +x /tmp/wp-cli.phar
  php /tmp/wp-cli.phar core version --path=/var/www/html --allow-root
"

La même approche est utilisée pour Composer :

docker compose exec wordpress bash -lc "
  curl -sSL -o /tmp/composer.phar https://getcomposer.org/composer-stable.phar
  chmod +x /tmp/composer.phar
  php /tmp/composer.phar --version
"

Ces deux commandes peuvent aussi être lancées via make terminal une fois dans le shell du conteneur. Chaque vérification fonctionnelle décrite sur cette page (activation du thème, inspection de la base de données, compilation des traductions, notice WooCommerce) a été validée de cette façon, contre l'installation WordPress réelle.

Dépendances PHP et interfaces

Le thème utilise Composer pour ses dépendances PHP, chargées automatiquement sous l'espace de noms Solar_Template\ (PSR-4, mappé sur inc/). Le code métier n'appelle jamais directement une librairie tierce : il dépend d'une interface définie sous Solar_Template\Contracts\*, avec une implémentation par défaut fournie sous Solar_Template\Support\* (ou un espace de noms dédié pour les sous-systèmes plus larges, ex. Solar_Template\I18n\*). Chaque dépendance reste ainsi remplaçable sans toucher au code qui la consomme. 

composer install   # installe les dépendances + génère l'autoload
composer lint      # vérifie la norme de code (WordPress-Extra, via PHP_CodeSniffer)
composer format    # corrige automatiquement ce qui peut l'être (phpcbf)

Un clone récent de ce thème n'embarque pas de dossier vendor/. Le thème s'active tout de même sans lui — il affiche une notice d'administration invitant à lancer composer install plutôt que de provoquer une erreur fatale.

Configuration du thème (.env)

Le thème lit ses propres réglages non sensibles (version, mode de build des assets, TTL du cache) depuis un fichier .env à sa racine, copié depuis le .env.example versionné. Il est entièrement distinct du .env du dépôt parent wordpress-dev-env : aucun nom de variable en commun, et ce thème ne lit ni ne stocke jamais les identifiants de connexion à la base de données — ceux-ci restent gérés par le dépôt parent.

Pipeline de compilation des assets

Les sources SCSS/JS vivent dans assets/scss/ et assets/js/ et sont compilées par Vite vers assets/dist/main.css / assets/dist/main.js. 

npm install       # installe les dépendances
npm run build     # build de production ponctuel (sans sourcemap)
npm run dev       # recompile en continu (développement, avec sourcemap)
npm run format    # formate assets/**/*.{js,scss} avec Prettier

Le thème ne charge les fichiers compilés que s'ils existent, avec un anti-cache basé sur la date de modification du fichier — l'absence de build signifie simplement l'absence de CSS/JS personnalisé (plus une notice d'administration), jamais une erreur fatale.

Système de traduction

Les gabarits du thème continuent d'appeler partout les fonctions de traduction natives de WordPress — __(), _e(), _n() — avec le text-domain solar-template, comme n'importe quel autre thème. Ce qui est spécifique, c'est l'origine du texte traduit : plutôt que de livrer des fichiers .po/.mo édités à la main, le thème stocke chaque chaîne dans deux tables de base de données (wp_solar_template_languages, wp_solar_template_translations) modifiables depuis les futurs écrans d'administration du thème, et les compile en fichiers .mo standards à chaque modification. WordPress charge ensuite ces fichiers normalement — rien ne change dans la façon dont les gabarits lisent les traductions.

Le français (fr_FR) et l'anglais (en_US) sont pré-installés ; ajouter une autre langue ne nécessite jamais de toucher au code du thème.

TableRôle
wp_solar_template_languagesLangues installées : code, libellé, drapeau, active/défaut
wp_solar_template_translationsCatalogue : clé → texte singulier/pluriel par langue

À noter : le dossier languages/ propre à un thème attend des fichiers .mo nommés {locale}.mo (ex. fr_FR.mo) — pas {text-domain}-{locale}.mo, format requis uniquement pour le dossier partagé wp-content/languages/themes/. C'est ce que produit DatabaseTranslator::compile().

Détection de WooCommerce

Le thème ne nécessite pas WooCommerce pour s'activer. Si WooCommerce est absent ou inactif, une notice d'administration invite l'administrateur du site à l'installer/l'activer, et le support WooCommerce spécifique du thème est gracieusement ignoré plutôt que de provoquer une erreur fatale.
